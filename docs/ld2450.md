# LD2450 ground-truth recording

## Hardware safety

The LD2450 module is powered from 5 V, while its UART data lines use 3.3 V
logic. Never connect a UART data line to 5 V.

| LD2450 | ESP32-S3 DevKitC-1 |
|---|---|
| VCC | 5V/VBUS |
| GND | GND |
| TX | GPIO16 / UART RX |
| RX | GPIO17 / UART TX |

UART settings are 256000 baud, 8 data bits, no parity, and 1 stop bit. Verify
the actual board pin assignment against the firmware configuration before
powering the setup.

## Status

The firmware, physical UART path, parser, MQTT publisher, and synchronized host
recording path have been validated on hardware. The 7 August acceptance run
recorded RX1 CSI and LD2450 ground truth continuously for 609 seconds without a
UART error, MQTT publish failure, queue drop, node-offline transition, or radar

The validated bench setup uses an ESP32-C5 board only as a stable 5 V source
for the radar. The ESP32-S3 remains the UART, Wi-Fi, and MQTT bridge. This power
arrangement must remain documented until the S3-side 5 V path is repaired or a
dedicated regulated 5 V supply replaces the C5. A longer 30-minute stability
run remains an optional follow-up; it is not part of the completed 10-minute
Week 5 acceptance run.

## Electrical connection

Disconnect USB power before changing any wire.

| Radar connector | Harness color | Validated connection | Purpose |
| --- | --- | --- | --- |
| GND | Yellow | ESP32-C5 GND, then C5 GND to S3 GND | Common ground |
| TX | White | GPIO18 / UART2 RX | Radar data to ESP32 |
| RX | Red | GPIO17 / UART2 TX | ESP32 commands to radar |
| 5V | Black | ESP32-C5 5V | Radar power |

The harness colors are specific to the supplied cable and do not follow common
power-wire conventions. Always verify the radar connector labels rather than
assuming a function from color. The radar power input is 5 V and its UART IO
level is 3.3 V. Do not connect the radar UART pins to 5 V.

Power the C5 and S3 from their own USB connections. Do not connect the C5 5 V
rail to the S3 5 V rail. Only the grounds are shared between the two boards.
The C5 runs no part of the VSense bridge firmware in this setup; it supplies
radar power only.

These are profile defaults, not hard-coded runtime assumptions. Generate and
review a separate configuration for this board so an RX or TX node's existing
`sdkconfig` cannot leak into the radar build:

```bash
cd firmware
source ~/esp/esp-idf/export.sh

idf.py -B build-ld2450-01 \
  -D IDF_TARGET=esp32s3 \
  -D SDKCONFIG="$PWD/build-ld2450-01/sdkconfig" \
  -D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.defaults.ld2450_01' \
  menuconfig
```

Normal operation stays at the project-specified 256000 baud. Automatic baud
scanning remains available in Kconfig only as an explicit diagnostic option
for a radar whose persistent baud rate may previously have been changed.

## Root cause found in the firmware

The original radar role called the blocking Wi-Fi connection function before
installing the UART driver. If the configured access point was unavailable,
the call waited forever and GPIO18 was never initialized as the radar RX input.
That software ordering bug produces exactly the same visible symptom as an
unpowered radar: no received bytes and no parsed frames.

The UART driver and its diagnostic tasks now start before Wi-Fi. Radar input can
therefore be verified from the USB serial monitor even with a wrong Wi-Fi
password, an unavailable access point, or an offline MQTT broker.

## UART frame contract

LD2450 target reports are 30 bytes:

```text
AA FF 03 00 | target 1 (8) | target 2 (8) | target 3 (8) | 55 CC
```

Each target contains little-endian X position, Y position, speed, and distance
resolution fields. The stream decoder accepts fragmented UART reads, ignores
leading noise, and resynchronizes after a malformed candidate. An empty target
block is represented by eight zero bytes.

## MQTT contract

Ground-truth topic:

```text
vsense/gt/ld2450_01
```

Firmware payload:

```json
{
Example firmware payload:

```json
{
  "schema_version": 1,
  "message_type": "ground_truth",
  "node_id": "ld2450_01",
  "ts_us": 123456789,
  "frame_seq": 42,
  "targets": [
    {
      "target_id": 1,
      "x_mm": -782,
      "y_mm": 1713,
      "speed_cm_s": -16,
      "distance_mm": 1883,
      "resolution_mm": 320
    }
  ]
}
```

An empty `targets` list is a valid no-target frame. `distance_mm` is accepted
when present; the other target fields are required. Topic identity is
authoritative, so the collector records the node as `ld2450_01` even if the
payload contains a conflicting `node_id`.

The collector adds `schema_version`, `message_type`, `mqtt_topic`,
`recorded_at`, `collector_ts_us`, and `session_id`. Device `ts_us` clocks are
independent. CSI and radar must be aligned with the common `collector_ts_us`
clock, not device `ts_us`.

## Recording campaign

Start one scenario recording from the repository root:

```bash
python server/session_cli.py start \
  --scenario walking \
  --repeat 1 \
  --operator busra \
  --subject participant_01 \
  --location lab
```

Inspect and stop it:

```bash
python server/session_cli.py status
python server/session_cli.py stop
```

If the MQTT broker is on another machine, add `--host BROKER_IP` to `start`.
The supported campaign scenarios are `empty_room`, `walking`, `sitting`,
`standing`, and `desk_work`.

Each session is stored under:

```text
dataset-v1/sessions/<session_id>/
├── csi.jsonl
├── ground_truth.jsonl
├── telemetry.jsonl
├── metadata.json
├── labels.json
└── session.log
```

After stopping, validate the ten-minute duration, both RX streams, radar
frames, and the 200 ms synchronization requirement:

```bash
python server/validate_session.py dataset-v1/sessions/<session_id>
```

For a short pilot, lower only the duration requirement:

```bash
python server/validate_session.py dataset-v1/sessions/<session_id> \
  --min-duration-seconds 30
```

Keep raw JSONL files unchanged. Create later Parquet/ML outputs from copies of
these normalized records.
`ts_us` is ESP32 uptime and must not be compared directly with another device's
uptime. The collector adds `collector_ts_us` and `recorded_at` when the MQTT
message arrives. CSI-to-radar alignment uses `collector_ts_us`.

Status and health topics:

```text
vsense/ld2450_01/status
vsense/ld2450_01/health
```

Radar health includes UART byte/frame counts, invalid frames, overflow count,
frame/parity error counts, the actively tested baud rate, baud scan count, queue
drops, MQTT success/failure counts, target count, and last-frame age.

The serial health line is sufficient to isolate the failure without MQTT:

| Serial result | Interpretation |
| --- | --- |
| `bytes=0` at 256000 baud | No electrical activity reaches GPIO18: check radar 5 V, common GND, connector order, TX wire, or radar hardware |
| `bytes>0`, no valid frame | A signal reaches GPIO18 but it is noise, a changed radar baud rate, the wrong pin/source, or not an LD2450 data stream |
| `frame_err` or `parity_err` rises | Signal integrity, ground, or UART format problem |
| `frames` rises and `invalid=0` | Radar-to-ESP UART path and parser are working |
| `frames` rises but `published=0` | Radar is working; the remaining fault is Wi-Fi/MQTT |

At the first received bytes the firmware prints a short hex sample. A valid
stream is confirmed when it later prints a 30-byte frame beginning with
`AA FF 03 00` and ending with `55 CC`.

## Collector handoff

The current `server/mqtt_collector.py` explicitly subscribes to
`vsense/gt/+`, recognizes the four-part radar topic, validates the ground-truth
payload, and normalizes it without changing the firmware topic. It adds a
common collector timestamp to both binary CSI and JSON radar messages:

Expected normalized record additions are:

```json
{
  "collector_ts_us": 0,
  "recorded_at": "2026-08-03T00:00:00Z"
}
```

With `--session-dir`, the collector writes `csi.jsonl`,
`ground_truth.jsonl`, and `telemetry.jsonl` separately under one shared session
identifier. Use `collector_ts_us`, not device-local `ts_us`, for CSI-to-radar
alignment.

## Hardware-free ground-truth simulation

Person A can generate deterministic LD2450-compatible messages while physical
hardware is unavailable. The simulator is independent of the firmware build
and does not modify TX/RX nodes.

Preview two targets locally at 10 Hz for one second:

```bash
python3 server/ld2450_simulator.py \
  --transport stdout \
  --rate-hz 10 \
  --duration-seconds 1 \
  --target-count 2
```

Publish the same contract to the local MQTT broker:

```bash
python3 server/ld2450_simulator.py \
  --transport mqtt \
  --broker-host 127.0.0.1 \
  --broker-port 1883 \
  --topic vsense/gt/ld2450_01 \
  --node-id ld2450_01 \
  --rate-hz 10 \
  --duration-seconds 30 \
  --target-count 1
```

The simulator intentionally does not add `collector_ts_us` or `recorded_at`.
Those fields belong to the collector receive path.

Run its hardware-free contract tests with:

```bash
cd server
python3 -m unittest -v test_ld2450_simulator.py
```

## Diagnosing a physical radar input failure

Use two terminals so firmware health and MQTT telemetry corroborate each
other. In terminal one, monitor the already-flashed bridge:

```bash
cd firmware
idf.py -B build-ld2450-01 \
  -p /dev/cu.usbmodem2101 monitor
```

In terminal two, capture one complete health record:

```bash
mosquitto_sub \
  -h 127.0.0.1 \
  -p 1883 \
  -t 'vsense/ld2450_01/health' \
  -C 1 -v
```

The bridge, Wi-Fi, and MQTT path are healthy when the boot log reports the
LD2450 role, obtains an IP address, and connects to the broker. A persistent
`uart_bytes_received: 0` while `frames_received`, `frames_invalid`, and
`uart_overflow` also remain zero demonstrates that the ESP UART input received
no electrical data from the radar. This evidence isolates the failure before
the parser and MQTT ground-truth publisher; it does not by itself distinguish
radar power, cable continuity, or a faulty radar TX output.

This diagnostic previously isolated the supplied S3-side radar power path. The
same radar became visible in HLK RadarTool when powered from the C5, then
returned valid command acknowledgements and target frames over the documented
GPIO18/GPIO17 UART wiring. The successful acceptance run confirms that the
radar, UART wiring, parser, and MQTT publisher are operational.
